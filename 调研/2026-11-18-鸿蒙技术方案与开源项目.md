# HiFairy 鸿蒙技术方案与开源项目调研

日期：2026-11-18。依据项目简述与长期原则，重点评估纯鸿蒙适配、Fairy 主题体验、低延迟语音和维护成本。下文的“建议”是技术判断，尚非已确认的产品决策。

**后续决策（2026-11-18）：用户确定先做 Android APK，经 HarmonyOS 7 手机上的兼容环境运行；再做原生鸿蒙版。下文“原生首选”保留为调研时的长期技术判断，实施顺序以本决策为准。**

## 一、先明确交付目标

纯鸿蒙原生应用应以 **HAP/APP** 打包，不是 Android APK。若还要给 Android 手机安装，须另立跨平台目标；ArkUI-X 可作为后续候选，但会增加适配与测试面。华为的 Stage 模型是长期演进方向，ArkTS 项目的 `entry` 模块可编译为 HAP。[华为 Stage 文档](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/stage-model-development-overview/) · [华为项目结构文档](https://developer.huawei.com/consumer/en/doc/harmonyos-guides-V5/start-with-ets-stage-V5) · [华为开发者论坛关于包格式的说明](https://developer.huawei.com/consumer/cn/forum/topic/0203229196583327316)

## 二、技术路线比较

| 方案 | UI 与动效 | 纯鸿蒙适配 | 维护成本 | 判断 |
| --- | --- | --- | --- | --- |
| ArkTS + ArkUI + Stage 原生 | 可按设计系统封装组件、动画、手势 | 最直接 | 中 | **首选**：围绕目标设备与体验设计 |
| Web 页面 + WebView | 参考插件 CSS/SVG 可复用较多 | 需原生壳与桥接 | 初期低，长期高 | 适合原型，不宜作为性能与交互基线 |
| ArkUI-X 跨平台 | ArkUI 代码可跨端 | 需额外 Android 适配 | 较高 | 仅在明确需要 Android APK 时评估 |

建议先用 ArkUI 原生建立 `design tokens → 基础组件 → 页面 → 状态/数据服务` 四层。主题 token 至少涵盖色板、字体层级、间距、圆角、描边、阴影、动效时长及缓动；眼徽维护 `idle/listening/thinking/speaking/error` 状态机。开机动画应可跳过、可重播，并与后续问好、眼徽过渡形成单一流程。低端设备与系统“减少动态效果”设置应纳入验证。这些属于项目设计建议，需要真机验证。

## 三、DeepSeek 官方 API

官方 Chat Completions 文档当前列出 `deepseek-flash` 与 `deepseek-v4-pro`，支持 `thinking` 开关和 `reasoning_effort` 的 `none/low/high/max`；默认与兼容映射可能变化。模型列表 API 会返回能力和支持的强度，故模型选择器宜通过 API 查询并缓存，而不是把模型名硬编码进界面。流式输出应驱动逐字展示、停止生成、错误恢复与语音分句队列。[官方 Chat API](https://api-docs.deepseek.com/api/create-chat-completion/) · [模型列表 API](https://api-docs.deepseek.com/api/list-models/) · [思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)

建议把 API 客户端、模型目录、会话仓储、语音管线和 UI 状态分离。用户自填 API Key 应保存在设备安全存储，不放源码、普通配置文件或日志。聊天历史适合结构化本地数据库；轻量设置可用 Preferences，华为提供 ArkTS Preferences API。[华为 Preferences 文档](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/data-persistence-by-preferences/)

## 四、开源项目可复用性

| 项目 | 可复用内容 | 迁移成本与限制 |

| [Fairy-DSH](https://github.com/Chengzhibense/Fairy-DSH) | 眼徽造型与动效溯源 | 参考插件声明其为 Apache-2.0 来源，复用时保留对应 NOTICE。 |
| [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) | 离线流式 ASR、TTS、VAD；仓库含 HarmonyOS 目录和构建工作流 | 适合作为原生语音首个 PoC；需实测模型体积、首字延迟、中文识别和设备兼容。代码 Apache-2.0。 |

| [GPT-SoVITS](https://github.com/RVC-Boss/GPT-SoVITS) | Fairy 音色还原的服务端候选 | 插件实际依赖外部 Python、权重与参考音频；仓库不包含完整手机端方案。首轮延迟、常驻内存、音色权利均需实测或核验。 |

## 五、语音体验建议与验证指标

优先做两条可比较的 PoC：A 为 sherpa-onnx 在鸿蒙端同时承担流式识别和本地合成；B 为 Vosk 本地识别加 GPT-SoVITS 远端常驻服务合成。B 更有机会接近目标音色，但增加网络往返和服务维护。参考插件的语音接口返回缓存 WAV URL，README 提到 CPU 加载约 20 秒，不能推断手机端会有同样速度。应改用常驻引擎、按标点分句、并行合成和 PCM 流式播放等方案做验证。鸿蒙 `AudioRenderer` 可用于 PCM 音频播放。[参考插件语音说明](https://github.com/AssassinVIX/fairy-zzz-plugin#readme) · [华为 AudioRenderer 文档](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/using-audiorenderer-for-playback/)

PoC 在目标真机上记录：按下麦克风到首个识别字、说话结束到最终文本、收到首个回复 token 到首帧声音、冷启动/热启动耗时、内存峰值、模型包体积、耗电与中文错误率。目标阈值需由真实基线和用户体感共同确定，不能在未测设备上预设。

## 六、实施顺序与待确认方向

当前实施顺序调整为：先建立 Android APK 工程并在目标手机的兼容环境验证安装、更新、麦克风、音频播放、后台行为和动画帧率；再完成主题、DeepSeek 会话与语音功能。业务逻辑、设计 token、动效规格、数据模型和接口契约应保持平台无关，供后续 ArkTS/ArkUI 原生版复用。Android UI 代码不应假定能直接移植到 ArkUI。

1. 建原生 ArkTS/ArkUI 工程和主题 token，先完成三张参考界面的静态版与状态切换。
2. 把参考插件的眼徽几何、时长、状态映射整理成可追溯的设计规格；在 ArkUI 重建启动、问好与眼徽交互。
3. 接 DeepSeek 流式会话、模型能力查询、历史记录和本地安全配置。
4. 在真实 HarmonyOS 7 设备做两条语音 PoC，按上述指标选择实现。
5. 完成可访问性、长会话性能、后台/中断、弱网与断网验证，整理许可清单和发布素材。

需要用户最终定方向的两点：是否只面向纯鸿蒙，还是同时交付 Android APK；Fairy 原版角色素材与音色是仅供个人使用，还是计划公开发布。后者影响素材授权和替代设计。
